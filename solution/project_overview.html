Feature Engineering Pipeline

Raw inputs are transformed into ML-ready features:

Temporal Features
  • hour_sin = sin(2π × hour/24)
  • hour_cos = cos(2π × hour/24)
  • is_peak_am = hour ∈ [7,9]
  • is_peak_pm = hour ∈ [16,18]
  • is_weekend = dow ≥ 5
Why circular? Hour 23 and 0 are adjacent, not maximally different.
Spatial Features
  • intersection_id = 0,1,2,3
  • direction_id = N,S,E,W encoded
  • ns_direction = is N or S?
Why ns_direction? Commuter patterns differ NS vs EW.
Interaction Features
  • hour × is_weekend
  • peak × direction
  • weather = 0,1,2
Why interactions? Weekend rush differs from weekday.

Key: As time progresses (7 AM → 8 AM → 9 AM), ML predictions change automatically. At 7:45 AM, ML predicts rush is coming → green time shifts to NS before queues build.
ML → Flow Ratios Pipeline:
ML predicts 4 directional rates per intersection:
  mlPredict(north) → 0.14  |  mlPredict(south) → 0.12  |  mlPredict(east) → 0.05  |  mlPredict(west) → 0.04

Aggregate by axis (max of opposing directions):
  ns_pred = max(0.14, 0.12) = 0.14     ew_pred = max(0.05, 0.04) = 0.05

Why max()? Both N and S get green simultaneously — the limiting direction determines green time needed. 
# Step 1: Blend ML prediction with queue feedback
ns_pred = max(ml_rates['north'], ml_rates['south'])  # e.g., 0.42 veh/s
ew_pred = max(ml_rates['east'], ml_rates['west'])    # e.g., 0.08 veh/s

ns_queue = (queue['north'] + queue['south']) / 20 * 0.5  # normalize
ew_queue = (queue['east'] + queue['west']) / 20 * 0.5

ns_demand = 0.7 * ns_pred + 0.3 * ns_queue  # blended signal
ew_demand = 0.7 * ew_pred + 0.3 * ew_queue

# Step 2: Calculate flow ratios (demand / saturation)
y_ns = ns_demand / 0.5  # saturation = 0.5 veh/s
y_ew = ew_demand / 0.5
Y = min(y_ns + y_ew, 0.97)  # cap to prevent division issues

# Step 3: Webster's optimal cycle formula
L = 4  # lost time per cycle (startup delay)
C_optimal = (1.5 * L + 5) / (1 - Y)  # e.g., 60 seconds
C = clamp(C_optimal, MIN_CYCLE=24, MAX_CYCLE=120)

# Step 4: Allocate green time proportionally
effective = C - L  # usable green time
ns_green = effective * (y_ns / Y)  # e.g., 45 seconds
ew_green = effective * (y_ew / Y)  # e.g., 11 seconds

# Step 5: Enforce safety constraints
ns_green = max(ns_green, MIN_GREEN=10)  # pedestrian safety
ew_green = max(ew_green, MIN_GREEN=10)

Incident Handling Flow

How the system adapts to lane blockages (accidents, construction):

1. Incident Triggered
triggerIncident(intersection=0, dir='north', capacity=0.15)
  • Lane capacity reduced to 15%
  • Arrival rate multiplied by capacity factor
  • Queue builds faster on blocked direction
2. System Response
  • ML: Still predicts normal demand (no incident data)
  • Queue feedback (30%): Detects spike immediately
  • Optimizer: Increases green time for blocked direction
  • Result: 36.6% improvement vs baseline during incident
Why 30% queue feedback matters: The ML model was trained on normal traffic patterns — it can't predict accidents. The 30% queue weight lets the system react to unexpected events that ML hasn't seen. This is why Pure ML (100%) performs worse than hybrid during incidents.

Simulation Physics

How vehicles are modeled in TrafficSimulator:

ComponentModelParametersRationale
Arrivals Poisson process λ = predicted rate × dt Standard traffic flow model; memoryless arrivals
Queue discharge Deterministic + random min(queue, 0.5 × dt + rand) Saturation flow = 0.5 veh/s with some variability
Wait time Cumulative +1s per step in queue FIFO queue; first arrived = first served
Light phases Two-phase NS green ↔ EW green Simplified; no turn phases or pedestrian phases
Update frequency Every 60 seconds Timings recomputed Balance responsiveness vs stability
Steady-State Assumption: Each intersection is modeled independently — vehicles depart but don't travel to adjacent intersections. This simplifies the model while capturing core optimization dynamics. For network effects, you'd need Cell Transmission Model (CTM) or SUMO.

Why LightGBM Was Chosen

1. Best MAE (0.00545)

Lowest prediction error means more accurate demand forecasts. Even small MAE differences compound over thousands of timing decisions — 0.002 veh/s error × 3600s = 7 extra cars misallocated per hour.

2. Fastest Training (0.3s)

7× faster than Random Forest. Critical for real-world deployment where models may need retraining daily with new data. LightGBM's histogram-based algorithm scales efficiently.

3. Best Wait Reduction (40.1%)

End-to-end benchmark: LightGBM predictions fed to Webster optimizer achieved highest wait time improvement. This is the metric that matters — not just prediction accuracy, but traffic outcomes.

Runner-up Analysis: Random Forest (MAE=0.00547, 39.8% improvement) was nearly identical in accuracy but 7× slower to train. XGBoost (MAE=0.00574) showed slight overfitting on peak hours. Optimization Algorithm Comparison

Webster's Optimal Cycle Formula (1958)
C* = (1.5L + 5) / (1 − Y)
L = lost time per cycle (4s)  |  Y = sum of flow ratios (demand/saturation)

Algorithm Comparison

Algorithm Type ML Weight Avg Wait Improvement 20% Target
Fixed 30/30 Baseline — 7.5s 0% BASELINE

How Each Algorithm Works

Webster's Formula
Traffic engineering gold standard (1958)
  • Minimizes total delay mathematically
  • Adapts cycle length to demand (Y)
  • Splits green proportionally by flow ratio
C* = (1.5L + 5) / (1 − Y)
Max Pressure
Queue-based reactive control
  • Compares NS vs EW queue pressure
  • Greedy: serves highest queue first
  • No prediction, pure reaction
green = argmax(queue_ns, queue_ew)
Proportional
Simple ratio-based allocation
  • Divides green time by queue ratio
  • Fixed cycle, variable split
  • Less aggressive than Max Pressure
ns_green = C × (q_ns / (q_ns + q_ew))
Why Webster + ML Won:
  • Max Pressure reacts to current queues but can't anticipate — causes oscillation during rush hour transitions
  • Proportional smooths allocation but still purely reactive — same anticipation problem
  • Webster + ML predicts demand before queues build, then fine-tunes with 30% queue feedback for unexpected events

Why 70% ML + 30% Queue?

ML Prediction (70%)
  • Anticipates demand before queues build
  • Captures time-of-day patterns
  • Accounts for weather effects
Queue Feedback (30%)
  • Reacts to unexpected spikes
  • Corrects prediction errors
  • Handles incidents immediately
