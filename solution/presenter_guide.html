Presenter Guide: Traffic Light Optimization

Purpose: This guide provides talking points and thought process explanations for presenting the project. Each section maps to the project_overview.html structure. Tags indicate which grading criterion each point supports: ML OPT ENG

1. Executive Summary ~2 min

Opening Hook

Lead with the result: "This system reduces average vehicle wait time by ~28% across scenarios — up to 57% during PM Rush — in a connected 2×2 intersection network. During rush hours, the optimizer also achieves 17% higher throughput, meaning more vehicles complete their journeys through the network."

Key Metrics to Mention

Explain each metric briefly:
  • ~28% avg wait reduction — across all scenarios (up to 57% PM Rush)
  • +17% throughput — more vehicles complete journeys during rush hours
  • R² = 0.985 — model explains 98.5% of variance in traffic demand
  • Gini = 0.94 — ranking quality for prioritizing green time
I chose to highlight multiple metrics because a single metric can be misleading. R² shows prediction accuracy, but Gini shows whether the model correctly prioritizes which direction needs more green time — that's what actually matters for optimization.
"These metrics seem very high — is this overfitting?"
Good observation. The high scores are expected because we're using synthetic data with deterministic patterns (rush hours at 8am/5pm). Cross-validation shows train/val gap under 10%, so the model generalizes within this distribution. Real-world deployment would need validation on actual sensor data.

2. System Architecture ~3 min

The Five-Layer Architecture

Walk through each layer: "The system has five distinct layers, each with a single responsibility:"
1. DATA LAYER ML
  • Purpose: Generate synthetic traffic patterns + feature engineering
  • Key files: ml_model.py (generate_training_data, add_features)
  • Output: 11,520 rows × 12 features (30 days × 24 hours × 4 intersections × 4 directions)
  • Key insight: Cyclic encoding (hour_sin/cos) preserves 11pm→midnight adjacency
2. ML PREDICTION LAYER ML
  • Purpose: Predict arrival rates per direction per intersection
  • Model: LightGBM (R²=0.985, Gini=0.94, lowest MAE)
  • Output: 4 rates per intersection {north, south, east, west}
  • Key insight: Prediction enables PROACTIVE green allocation before rush hour
3. OPTIMIZATION LAYER OPT
  • Purpose: Convert demand predictions to green timing splits
  • Algorithm: Webster's formula (1958) — mathematically optimal cycle length
  • Hybrid: 70% ML prediction + 30% queue feedback
  • Constraints: MIN_GREEN=10s, MAX_CYCLE=120s, MIN_CYCLE=24s
  • Key insight: ML anticipates demand, queue feedback handles unexpected events
4. SIMULATION LAYER ENG
  • Purpose: Model vehicle physics + network flow
  • Key files: simulator.py (TrafficSimulator, Intersection, Vehicle)
  • Physics: Poisson arrivals, FIFO queues, saturation flow 0.5 veh/s
  • Network: 2×2 grid, vehicles route through multiple intersections
  • Key insight: Vehicles colored by origin shows network flow dynamics
5. VISUALIZATION LAYER ENG
  • Purpose: Real-time demo + static figures for documentation
  • demo.html: Browser-based, zero install, full GUI controls
  • TrafficDemo.exe: Standalone Python with actual LightGBM model
  • Key features: Side-by-side comparison, origin-colored vehicles, live charts
  • Key insight: Working visualization validates simulation physics visually
I separated ML from optimization deliberately. The ML model predicts demand, but the optimizer decides green splits. This means we can swap in different ML models OR different optimization algorithms independently — good software design principle.

Swimlane Diagram

Explain the data transformation: "Raw data (30 days × 24 hours × 4 intersections × 4 directions = 11,520 rows) gets transformed through feature engineering, fed to LightGBM, and outputs arrival rates per direction. The optimizer then converts rates to green timings."
"Why not use a single end-to-end model that directly outputs green timings?"
Two reasons: (1) Interpretability — we can inspect predicted demand separately from optimization logic. (2) Constraints — Webster's formula guarantees we satisfy MIN_GREEN, MAX_CYCLE constraints. A pure neural net might violate safety constraints.

Technical Deep Dive (if time allows) ML OPT

Feature Engineering Pipeline: "Three categories: Temporal (hour_sin, hour_cos, is_peak_am, is_peak_pm, is_weekend), Spatial (intersection_id, direction_id, ns_direction), and Interaction (hour×weekend, peak×direction, weather). 12 features total."
ML → Flow Ratios: "ML outputs 4 rates per intersection (N, S, E, W). We aggregate by axis using max(): ns_pred = max(N, S), ew_pred = max(E, W). Why max? Both N and S get green simultaneously — the higher-demand direction determines green time needed. These then blend with queue feedback before Webster's formula."
Optimization Step-by-Step (recalculated every 60s):
  1. Blend: ns_demand = 0.7 × ML_prediction + 0.3 × queue_signal
  2. Flow ratios: y_ns = ns_demand / 0.5, y_ew = ew_demand / 0.5, Y = y_ns + y_ew (capped at 0.97)
  3. Webster: C* = (1.5L + 5) / (1 − Y) → cycle length adapts to demand
  4. Split: ns_green = (C − L) × (y_ns / Y) → proportional to flow ratio
  5. Constrain: Enforce MIN_GREEN=10s, MAX_CYCLE=120s
Incident Handling: "Key insight: ML can't predict accidents. When incident occurs, capacity drops to 15%, queues spike. The 30% queue feedback detects this immediately and increases green time. Result: 36.6% improvement even during incidents."
"Walk me through what happens when a car arrives at the intersection?"
Poisson process generates arrivals (λ = predicted rate). Car joins queue. Each timestep, wait counter increments. When light turns green, saturation flow (0.5 veh/s) discharges queue FIFO. Departed cars contribute their wait time to average. Simple but physically grounded.

3. ML Model Comparison ~4 min

Model Selection Process ML

Explain the comparison: "I evaluated 5 models: LightGBM, XGBoost, Random Forest, Gradient Boosting, and Ridge Regression. LightGBM won on three criteria: lowest MAE, fastest training, and best wait time reduction in simulation."
I didn't just pick the model with best R² — I measured actual simulation performance. XGBoost had slightly higher R² but lower wait time reduction. The real-world metric (wait time) is what matters, not the proxy metric (R²).

Feature Engineering ML

Highlight the key insight: "The most important feature engineering decision was circular encoding for hour. Raw hour (0-23) treats 11pm and midnight as maximally different, but they're actually adjacent. Sin/cos encoding preserves this cyclical relationship."
Peak flags rationale: "Instead of 24 one-hot columns for hour, I used two binary flags: is_peak_am (7-9) and is_peak_pm (16-18). This captures the key patterns with far fewer features, reducing overfitting risk."
"Why didn't you try neural networks or deep learning?"
For tabular data with 11,520 rows, gradient boosting typically outperforms neural networks. Deep learning shines with images, text, or massive datasets. I also wanted interpretability — SHAP analysis works well with tree-based models.

Feature Reduction Techniques Tested ML

What I tried:
Technique Result Decision
One-hot hour (24 cols) Overfitting, high variance Rejected
Cyclic encoding (sin/cos) 2 cols, preserves cyclical nature Selected
Peak flags only 2 cols (AM/PM rush), simple but effective Selected
PCA (dimensionality reduction) Lost interpretability, no accuracy gain Rejected
RFE (Recursive Feature Elimination) Confirmed top features match SHAP Validated
Correlation filtering (>0.9) Removed hour_cos (redundant with sin) Applied
Final model uses 12 features: hour_sin, hour_cos, is_peak_am, is_peak_pm, is_weekend, day_of_week, intersection_id, direction_id, ns_direction, and 3 interaction terms. This balances interpretability with predictive power.

4. SHAP Analysis ~3 min

Why SHAP? ML

Compare to alternatives: "SHAP provides three things Gini importance doesn't: (1) it's unbiased toward high-cardinality features, (2) it shows direction of impact (positive vs negative), (3) it's theoretically grounded in game theory (Shapley values)."

Key SHAP Insights

Validate domain knowledge: "SHAP confirmed our intuition: hour_sin is most important (captures rush hours), followed by is_peak_am. Weekend reduces demand by 40%. No unexpected features appeared in top 6 — this validates there's no data leakage."
SHAP isn't just for show — it caught a potential issue early. In an earlier version, intersection_id was ranked #1, which would mean the model was memorizing location-specific averages rather than learning patterns. After fixing feature engineering, hour_sin correctly became #1.
"What's the difference between Gini coefficient here and the Gini importance in tree models?"
Confusing naming! Tree Gini importance measures how often a feature is used in splits. The Gini coefficient (0.94) measures ranking quality — how well the model orders predictions. They're completely different metrics that happen to share a name.

5. Gini & ROC-AUC Analysis ~2 min

Why These Metrics Matter ML

Connect to the business problem: "For traffic optimization, ranking matters more than exact values. If I predict NS demand = 0.35 instead of 0.42, that's fine — as long as I correctly rank NS > EW. Gini coefficient measures exactly this ranking quality."
ROC-AUC for high-demand detection: "ROC-AUC = 0.97 means the model correctly identifies high-demand scenarios 97% of the time. This is critical because rush hours need proactive green allocation before queues build."
I included these metrics because R² alone can be misleading. A model could have good R² but poor ranking — it might predict the right average but confuse which direction has higher demand. Gini directly measures what matters for optimization.

6. Optimization Algorithm Comparison ~4 min

Webster's Formula OPT

Explain the formula: "Webster's 1958 formula: C* = (1.5L + 5) / (1 − Y). This is the mathematically optimal cycle length that minimizes total delay. L is lost time (4 seconds), Y is sum of flow ratios."
I chose Webster over more modern approaches (like SCOOT or SCATS) because: (1) it's analytically optimal for isolated intersections, (2) it's computationally trivial, (3) it's well-understood and auditable. For a 4-intersection demo, simplicity wins.

Optimization Approaches Tested OPT

What I evaluated:
Approach Wait Time Δ Complexity Decision
Fixed Timing (30/30) Baseline (0%) Trivial Control
Webster's Formula ~28% avg Low (analytical) Selected
Pure Queue-Reactive ~15% Low Too reactive
Max Pressure ~22% Medium Good, but Webster better
Green Wave Coordination Not tested (future work) High Scope limitation
Webster won because it's mathematically proven optimal for isolated intersections. Adding network coordination (green wave) would require solving a more complex coordination problem — documented as future work rather than forced into scope.

The 70/30 Blend OPT

Explain the hybrid approach: "Pure ML (100%) anticipates demand but can't react to unexpected events. Pure queue feedback (0% ML) reacts but can't anticipate. 70% ML + 30% queue gives the best of both worlds — tested empirically."
KEY POINT — What does ML actually contribute? "This is the critical question: if the optimizer works, why add ML? The answer is PREDICTION vs REACTION."
  • Without ML (Pure Queue): At 7:45 AM, queues are low → optimizer keeps equal splits. By 8:00 AM, queues explode → finally adjusts. 5+ minute lag.
  • With ML (Hybrid): At 7:45 AM, ML predicts rush coming → pre-allocates NS green time. Cars arrive to ready green phases. No delay.
  • Proof: In isolated tests: Pure Queue = 30.7%, Hybrid = 40.1%. In connected network: PM Rush shows 57% improvement. The ML contribution is clear.
This is a key differentiator. Without this explanation, it looks like we're adding ML for complexity's sake. The benchmark data proves ML adds real value — it's not just theoretical.
"Why 70/30 specifically? Did you tune this?"
Yes. I tested 100/0, 80/20, 70/30, 50/50, 30/70, 0/100 blends. 70/30 achieved the best wait time reduction. Higher ML weights performed slightly worse because they couldn't adapt to prediction errors fast enough.

Constraint Satisfaction OPT

Highlight safety constraints: "The optimizer enforces hard constraints: MIN_GREEN = 10 seconds (pedestrian safety), MAX_CYCLE = 120 seconds (driver patience), MIN_CYCLE = 24 seconds (physical minimum). These can never be violated."
Constraints matter for real-world deployment. A pure optimization that outputs 3-second green phases would be mathematically optimal but physically impossible and unsafe. Constraint satisfaction separates toy projects from production systems.

7. Code Structure ~2 min

Modular Architecture ENG

Explain the separation: "The src/ folder has four modules: ml_model.py (prediction), optimizer.py (green splits), simulator.py (physics), model_validation.py (metrics). Each module has one responsibility."
This separation lets us test each component independently. I can unit test the optimizer with mock ML predictions. I can benchmark different ML models without changing simulation code. Loose coupling = easier maintenance.

Entry Point ENG

Single command: "Running python main.py regenerates everything: trains the model, runs simulations, generates all 15 figures and 3 GIFs, saves the model. This reproducibility is critical for experiments."
"Why not use a notebook?"
Notebooks are great for exploration but bad for reproducibility. I used notebooks during development, then extracted the final code to .py files. main.py can run in CI/CD, notebooks can't easily.

Live Demonstration ENG

Demo talking points: "Notice how the optimized side pre-allocates green time to NS during morning rush. The baseline waits until queues build. That's the ML prediction in action. When we trigger an incident, watch how the 30% queue feedback kicks in to adapt."
"How does the connected network work?"
Vehicles enter the 2×2 grid at edge approaches, route through adjacent intersections, and exit at the opposite edge. Color-coding shows origin: Purple (Int 0), White (Int 1), Black (Int 2), Orange (Int 3). This creates realistic cross-intersection flow where congestion at one intersection backs up into adjacent queues — demonstrating the ML + optimization benefits across the network.
The demo exists because a working visualization is worth 1000 lines of code. Stakeholders can immediately see the impact of optimization without understanding the math. It also validates that the simulation physics are reasonable.

9. Scenario Benchmarks ~2 min

Where Optimization Excels OPT

Highlight the pattern: "PM Rush shows 57% improvement, Weekend 29%, Midday 36%. AM Rush is different — arrival rates exceed capacity (0.56 vs 0.5 veh/s saturation), causing unavoidable queue growth. The optimizer achieves +17% throughput but with higher wait times due to cascading congestion between intersections."
I included scenarios where optimization fails (midday, weekend) to show intellectual honesty. A presentation that only shows wins is suspicious. The failures validate that the improvements during rush hour are real, not artifacts.
"What about the AM Rush tradeoff?"
Great observation. AM Rush arrival rates (0.56 veh/s) actually exceed saturation capacity (0.5 veh/s) — queues MUST grow. The optimizer aggressively pushes NS vehicles downstream, causing cascading congestion (Int 0 → Int 2). The baseline's 50/50 split throttles this flow. Result: optimizer achieves +17% throughput but higher wait times. PM Rush rates (0.35 veh/s) stay under capacity, so we get wins on both metrics.

10. Limitations & Future Work ~2 min

Honest Limitations ENG

What we didn't do:
  • Independent optimization (each intersection optimizes locally, no green wave coordination)
  • Synthetic data (no real sensor validation)
  • 4 intersections (not city-scale)
  • No pedestrian modeling
Acknowledging limitations shows maturity. It also scopes future work clearly. A grader will respect honest assessment over overselling.

Future Work

Natural extensions:
  • Multi-agent RL: Coordinate adjacent intersections
  • Real sensor data: Validate on actual traffic patterns
  • Pedestrian priority: Add crossing demand
  • Emergency preemption: Override for ambulances/fire trucks

Closing Summary ~1 min

Three takeaways:
  1. ML + Optimization hybrid: Prediction anticipates demand, optimization satisfies constraints, queue feedback handles surprises
  2. Connected network model: ~28% avg wait reduction, up to 57% PM Rush, +17% throughput during rush hours
  3. Production-ready architecture: Modular code, working demo with origin-colored vehicles, reproducible benchmarks
Final thought: "Traffic optimization is a constrained optimization problem with uncertain inputs. The ML model handles uncertainty, Webster's formula handles optimization, and the constraint system handles safety. Each piece does one job well."
