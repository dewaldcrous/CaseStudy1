Key Terms — Start Here Before the Technical Sections

What is MAE?
MAE = Mean Absolute Error — the average size of the model's prediction mistake, in the same units as what it predicts.

MAE = (1/N) × Σ | predicted_value − actual_value |

Think of it as: "on average, how far off is the model?" It ignores whether the mistake is an over-prediction or an under-prediction — it only cares about the magnitude. N is the number of rows being evaluated.

Original Case Study Brief

A city operates a grid of signalised intersections currently controlled by fixed-time plans (30 s North–South green, 30 s East–West green). Traffic volumes follow strong temporal patterns — morning and evening peaks, directional asymmetry, weather sensitivity. The city wants to evaluate whether a machine-learning–driven adaptive controller can meaningfully reduce average vehicle wait times.

Critical Design Decision — Fair A/B Comparison
⚠️ Separation of demand_model and control_model A subtle but critical design choice: the pipeline uses two separate roles for ML models.

demand_model (always the best model): generates the arrival rates that define what traffic actually arrives in every simulation run. Identical across all runs — ensures every controller sees the same traffic volumes.

control_model (varies per run): used only by the WebsterOptimizer to decide green splits. For the baseline this is None; for optimized runs it varies from Ridge → RF → LightGBM to show how prediction quality affects timing quality.

Without this separation, using Ridge Regression as demand source would artificially lower arrival rates and make the baseline appear better — an invalid comparison.

Data Pipeline — Synthetic Traffic Generation

30 days of hourly traffic data are generated by six deterministic rules that encode well-established traffic engineering priors. The rules produce 11,520 rows (30 days × 24 hours × 4 intersections × 4 directions). Each rule is independently auditable and maps directly to documented real-world behaviour.

Rule A — Two-Peak Weekday Profile
f(h) = 0.015 + 0.20 · exp(−(h−8)² / 2) + 0.16 · exp(−(h−17.5)² / 3)

Two Gaussian humps centred at 8:00 (AM rush, σ²=1) and 17:30 (PM rush, σ²=1.5). The constants (0.20, 0.16) are calibrated so peak rates (~0.20 veh/s = 720 veh/hr) are roughly 10× higher than night-time (~0.015 veh/s = 54 veh/hr), consistent with real-world commuter patterns documented in HCM 6th Edition (TRB, 2016).

Rule B — Directional Asymmetry

During the AM rush, commuters travel from residential suburbs (north/south) into the city centre. During PM rush, they return (east/west). This is modelled as:

# AM weight: Gaussian centred at 8am
am_w  = exp(-(hour - 8.0)^2 / 2.0)

# NS multiplier: up to 3× during AM rush
ns_mult = 1.0 + 2.0 * am_w - 0.5 * pm_w   # range [0.5, 3.0]

# EW multiplier: up to 2.5× during PM rush
ew_mult = 1.0 + 1.5 * pm_w - 0.3 * am_w   # range [0.7, 2.5]

This asymmetry is exactly the regime where fixed 50/50 timing is most wasteful, and where Webster's formula provides the largest benefit.

Feature Engineering & Correlation Analysis

Model I/O contract X (feature matrix) — shape (N, 12), dtype float64. Every row describes ONE approach: one intersection × one direction × one hour × one day.
y (target variable) — arrival_rate, float, units veh/s, range ~0.005–1.2. This is what every model predicts. The predicted value feeds directly into Webster's formula as q_i → flow ratio y_i = q_i / saturation_flow → optimal cycle C*.
X shape at training time: (9,216 × 12) · at test time: (2,304 × 12) · at prediction time (inside simulator): (16 × 12) for 4 intersections × 4 directions.

4.2 Correlation with Target (arrival_rate)

Pearson r measures the linear association between each engineered feature and the target variable. A high |r| confirms the feature has real predictive signal for a linear model. Tree models can additionally exploit non-linear relationships.

Note on interpretation Low Pearson r does not mean a feature is useless. is_morning_rush creates a step-change (not a gradient) in arrival rate — this is a non-linear signal that Pearson r undervalues but tree models capture perfectly. SHAP values (Section 7) give the definitive contribution estimate.
[fig_correlation_analysis.png — run python main.py to generate]
Figure 4.1 — Left: Pearson r between each feature and arrival_rate (|r| sorted). Features above the orange threshold line show strong linear signal. Right: Feature cross-correlation matrix. Red cells indicate collinear pairs that may inflate Gini MDI importance scores.
4.3 Cross-Correlation — Multicollinearity Detection

The cross-correlation matrix reveals whether any engineered features move together strongly enough to be considered redundant. Key expectations:

  • hour_sin and hour_cos are by construction orthogonal (r = 0) — they carry independent phase information.
  • is_morning_rush and hour_sin will be positively correlated but not collinear — the rush flag has a different shape (binary step) than the continuous sine wave.
  • is_morning_rush and is_evening_rush should be uncorrelated (they span different hour windows).

Any pair identified with |r| > 0.80 is flagged. SHAP mean |φ| (Section 7) is then used to determine whether both contribute independently or one is truly redundant.

ML Model Comparison

All models are trained on days 0–24 (9,216 rows) and evaluated on days 25–29 (2,304 rows) — mimicking "predict next week from past history". This temporal split avoids data leakage and reflects production conditions where the model predicts forward in time.

Random Forest 100 bagged decision trees, max_depth=12, min_samples_leaf=4. Robust — averaging 100 trees reduces variance. No scaling needed. Well-calibrated feature importances. Slower inference than LightGBM. Memory-intensive with many trees.
Gradient Boosting sklearn sequential boosting, 150 trees, lr=0.08, max_depth=5. High accuracy. Sequential correction of residuals captures subtle patterns. Significantly slower than LightGBM. Risk of overfitting without early stopping.
LightGBM Microsoft histogram-based GBM. 200 trees, num_leaves=63, lr=0.05. 10–20× faster than sklearn GBM at similar or better accuracy. Leaf-wise (best-first) growth finds optimal splits faster. Model Enhancement & Reduction — FE · Sampling · Tuning · Feature Reduction

Three model-improvement strategies are evaluated independently and in combination. The primary evaluation metric is rush-hour MAE (hours 7–9am and 4–7pm on weekdays) rather than overall MAE. This is a deliberate business decision: prediction errors during rush hours have a disproportionate impact on timing quality and therefore on driver experience.

6.1 Strategy Descriptions
StrategyMethodBusiness Rationale
Feature Engineering Compare Base (12), Interactions (16), Rich (20) feature sets Interaction features (rush × direction) give the model direct access to the dominant demand signal, reducing the depth of trees needed and improving generalisation.
Importance Sampling Rush-hour rows weighted 3.0×; night rows weighted 0.4×. Also physical resampling: duplicate rush rows ×2, drop 65% of night rows. Directs the model's learning capacity toward the high-cost period. A 5% MAE improvement at rush hour is worth more operationally than a 20% improvement at 3am when queues are trivially short.

Searches: num_leaves (20–120), learning_rate (0.01–0.2), min_child_samples (5–50), n_estimators (100–400), subsample (0.6–1.0), colsample_bytree (0.6–1.0). 6.3 Deployment Threshold & Decision
Decision Rule Deploy the enhanced model only if: (1) rush-hour MAE improvement > 5% AND (2) overall R² remains > 0.97. This guards against overfitting to rush hours at the cost of generalisation quality.
⚠️ Honest conclusion: DO NOT deploy the enhancements (yet) The best enhancement (Combined) achieved only +0.6% rush-hour MAE improvement — far below the 5% threshold. This is noise, not signal. The base LightGBM model is already near the irreducible error floor for this data (the log-normal noise in Rule F sets a hard lower bound on achievable MAE). The mature engineering decision is to keep the simpler base model — it is faster to train, easier to maintain, and statistically indistinguishable from the enhanced variants. This negative result is itself valuable: it proves further model complexity would not pay off, redirecting effort toward data collection or sensor improvements instead.
On over/under-sampling specifically (your question) Both were tested in experiment 3 above. Over-sampling (resampling rush rows ×2) was neutral (−0.1%). Under-weighting night rows via sample weights (rush×3, night×0.4) actually hurt (−1.1%). Conclusion: the natural class balance is already adequate for tree models here — forcing the model to over-focus on rush hours traded away off-peak accuracy without a compensating peak-hour gain. Recommendation: train on the raw distribution.
6.4 Feature Reduction — Can We Use FEWER Features?

Enhancement asks "can more complexity help?" (barely). The equally important mirror question is "can we get away with less?" A leaner model has fewer live data feeds to maintain, infers faster, is more robust to sensor drift, and is easier to defend to a regulator. Likewise a naive top-6 permutation cut (+77.6%) dropped intersection_id, which carries real signal. The takeaway: use the Section 2b cross-correlation matrix to flag candidates, but let model-aware RFE make the final call — never drop a feature on linear correlation alone.

Model Validation — SHAP · Gini · Residuals · Learning Curves · Cross-Validation

Why seven validation tests? A single test MAE on a hold-out set answers one question: "how accurate is the model on average?" For a model that will influence real-time traffic control, stakeholders need answers to six additional questions — see below. Each test targets a different failure mode: (1) CV — is the score stable? (2) Importance — what drives it? (3) SHAP — why each prediction? (4) Residuals — where are systematic errors? (5) Learning curves — would more data help? (6) Gini — ranking skill? (7) AUC — can it flag high-demand situations?
7.1 Five-Fold Cross-Validation

Question: Is the test MAE stable or lucky?
Method: KFold(n=5, shuffle=False) — temporal ordering preserved to prevent future-data leakage. Reports mean ± std of MAE and R² across all folds.
Warning trigger: If train/val MAE gap exceeds 30%, the model is overfitting and depth / regularisation should be reduced before deployment.

This is textbook Gini bias: tree impurity importance over-values high-cardinality and continuous features. Had we trusted Gini alone, we would have wrongly concluded that intersection location matters more than rush hour — the opposite of the true data-generating process.

7.5 Gini Coefficient (Regression)

The Gini coefficient measures ranking quality: does the model correctly identify which hours/directions have high demand vs low demand? Defined as Gini = 2·AUC(Lorenz) − 1, with rows sorted descending by predicted value (credit-scoring convention, so Gini ∈ [0, 1] for a useful model).

Gini RangeInterpretationTraffic Context
> 0.85ExcellentModel correctly ranks demand in >85% of comparisons.
0.70–0.85GoodStrong ranking skill. Minor timing misallocations possible in edge cases.
0.50–0.70Moderate← Measured: 0.506. Acceptable ranking; see explanation below.
< 0.50WeakRanking skill needs improvement before deployment.
Confirmed Gini = 0.506 — why "moderate" despite R² = 0.9866? This apparent tension is the most instructive result in the validation suite, and it is not a contradiction:

1. The metrics measure different things. R² and MAE measure point-prediction accuracy (is the predicted number close to the actual?). Gini measures ranking discrimination (can the model order rows from highest to lowest demand?).

2. The data is dominated by low, similar values. Most of the 11,520 rows are off-peak hours where arrival rates cluster tightly around 0.01–0.08 veh/s. The model predicts these accurately (hence high R²), but ranking within a dense band of near-identical values is inherently noisy — tiny prediction errors reshuffle the order, which the Gini penalises heavily even though the absolute error is negligible.

3. It does not harm the optimizer. Webster's formula only needs the model to correctly identify which direction (NS vs EW) dominates at each intersection — a coarse, high-contrast distinction the model gets right (NS demand at 8am is 4× EW). The simulation results (40.1% improvement) confirm ranking quality is more than sufficient for the actual control decision. The moderate Gini reflects difficulty ranking near-identical off-peak rows, which are operationally irrelevant.

The model correctly treats it as a secondary modulator, not a primary driver — appropriate, since rain shifts volume by at most 25% versus the 10× swing between night and rush hour.
  5. The beeswarm confirms monotonic, sensible relationships. (c) SHAP explains the model, not ground truth — it confirms the model learned the rules, which is only as valid as the synthetic rules themselves.

Optimizer Design — Webster's Formula

The Webster (1958) optimal cycle formula was derived by minimising the total vehicle delay at a signalised intersection. It remains the industry standard for isolated intersection control and is specified in the Highway Capacity Manual 6th Edition (TRB, 2016).

8.1 The Formula
C* = (1.5 · L + 5) / (1 − Y)

L = total lost time per cycle = n_phases × 2s = 4s  ·  Y = Σ yi where yi = qi / s  ·  qi = arrival rate on critical approach  ·  s = saturation flow (0.5 veh/s)

8.2 Seven-Step Calculation Process
# Step 1: Get ML-predicted demand per phase (critical approach = max of N/S or E/W)
ns_pred = max(rate["north"], rate["south"])   # e.g. 0.22 veh/s at 8am
ew_pred = max(rate["east"],  rate["west"])    # e.g. 0.05 veh/s at 8am

# Step 2: Queue-derived demand signal (react to sudden spikes)
ns_q = (queues["north"] + queues["south"]) / 20.0 * 0.5

# Step 3: Blend ML and queue signal (α=0.7 ML weight)
ns = 0.7 * ns_pred + 0.3 * ns_q   # primarily ML-driven

# Step 4: Compute flow ratios y_i = demand / saturation
y_ns = ns / 0.5;   y_ew = ew / 0.5
Y    = min(y_ns + y_ew, 0.97)      # cap at 0.97 to keep C finite

# Step 5: Webster's optimal cycle length
C = (1.5 * 4 + 5) / (1 - Y)       # clipped to [24s, 120s]

# Step 6: Green split proportional to flow ratios
g_ns = (C - 4) * y_ns / (y_ns + y_ew)
g_ew = (C - 4) * y_ew / (y_ns + y_ew)

# Step 7: Enforce minimum green = 10s (pedestrian safety)
g_ns = max(g_ns, 10);   g_ew = max(g_ew, 10)

Why does the fixed split waste so much green? With NS demand 4.4× higher than EW, the optimal NS share is 81%. Fixed 50% gives NS only 50%, forcing NS queues to accumulate for 30s of red instead of 5–8s. Every extra second of red time adds vehicle-seconds of accumulated wait that cannot be recovered within the current cycle.
