Problem & Approach

Problem. A city grid of signalised intersections uses fixed 30 s / 30 s (NS/EW) timing regardless of demand. During the AM rush, NS demand can be 4× higher than EW — yet both directions receive equal green time. The requirement is a ≥ 20% reduction in average vehicle wait time.

Solution. A LightGBM model forecasts arrival rates (veh/s) per approach; Webster's (1958) optimal cycle formula allocates green splits proportional to the predicted flow ratios; the two strategies are compared in a physics-based queue simulation.

How the data tables were assembled — loop structure

Every row in the dataset is produced by a 4-level nested loop. The table below shows which rule fires at which level and what column it writes.

Loop levelIterates overRows per iterationRule applied hereColumns written
Level 1 — Day days 0–29 576 rows each Rule D — weather drawn once per day (55% clear / 30% cloudy / 15% rain) day, day_of_week, is_weekend, weather
Level 2 — Hour hours 0–23 24 rows each Rule A (weekday) or Rule C (weekend) — sets the base demand shape and directional multipliers hour, base rate, ns_mult, ew_mult (internal — not stored directly)
Level 3 — Intersection intersections 0–3 4 rows each Rule E (part 1) — intersection volume factor [1.0, 0.85, 1.2, 0.95] intersection_id, ifact (internal)
Level 4 — Direction north / south / east / west 1 row (record appended) Rule B direction multiplier + Rule E (part 2) direction factor + Rule F noise → final arrival_rate direction, direction_id, arrival_rate
How arrival_rate is assembled — the complete formula

Each record's target value is the product of all six rules applied in sequence:

# Level 1 — drawn once per day
weather_mult  = {clear: 1.00, cloudy: 1.05, rain: 1.25}[weather_type]    # Rule D

# Level 2 — computed per hour (weekday path)
base          = 0.015 + 0.20·exp(−(h−8)²/2) + 0.16·exp(−(h−17.5)²/3) # Rule A
ns_mult       = 1.0 + 2.0·am_weight − 0.5·pm_weight                      # Rule B (up to 3.0×)
ew_mult       = 1.0 + 1.5·pm_weight − 0.3·am_weight                      # Rule B (up to 2.5×)

# Level 3 — per intersection
ifact         = [1.0, 0.85, 1.20, 0.95][intersection_id]                  # Rule E

# Level 4 — per direction (one record appended per iteration)
dfact         = {north:0.9, south:1.1, east:1.0, west:0.95}[direction]    # Rule E
dm            = ns_mult if direction in (north, south) else ew_mult
noise         = lognormal(mean=0, σ=0.08)                                    # Rule F

arrival_rate = base × ifact × dfact × dm × weather_mult × noise    # TARGET y

Recommendation: Start with lagged demand and rolling averages — they're easy to implement and have the highest expected ROI. The real-time queue feedback is already in use (α=0.7 blend). Consider special events if the deployment area has stadiums, schools, or event venues.
Why 12 features are already near-optimal: Enhancement experiments (Section 5) showed that adding 8 more features (20 total) only improved rush-hour MAE by 0.5%. The current feature set already captures the dominant patterns (time-of-day, day-of-week, direction asymmetry, weather). Additional features help at the margins but won't dramatically change model performance because the underlying traffic patterns are fundamentally predictable from time and location.

Optimizer — Webster's Formula

C* = (1.5 · L + 5) / (1 − Y)

L = total lost time = 4s (2 phases × 2s)  ·  Y = Σ yi  ·  yi = qi / saturation_flow (0.5 veh/s)  ·  Green split ∝ yi / Y  ·  ML–queue blend: α = 0.7

Worked example — Monday 8am, Intersection 0
StepBaseline (Fixed)Webster Optimized
NS predicted demand0.65 veh/s (LightGBM)
EW predicted demand0.15 veh/s (LightGBM)
Y = Σ flow ratios—(0.65+0.15)/0.5 = capped at 0.97
Cycle C*60s (fixed)120s (high-demand cap)
NS green30s (50%)96s (80%)
EW green30s (50%)20s (17%)
ResultEW gets 30s it doesn't need; NS waits unnecessarilyGreen allocated where demand is

🚀 Recommended for presentation — Interactive Streamlit Dashboard streamlit run dashboard.py Opens http://localhost:8501 in your browser. Controls: Start/Pause, speed slider, scenario selector, live Plotly charts, ⚠ Trigger Incident button, ✓ Clear button.
Alternative — command-line animated demos (no browser needed): python main.py demo_am_rush    # Demo 1 — matplotlib window
python main.py demo_incident   # Demo 3 — matplotlib window
python save_demos.py          # Save all 3 as GIFs
DemoCommandDurationWhat it showsKey moment
1 — AM Rush demo_am_rush 300s simulated Monday 8am. NS demand is 4× EW. Webster gives ~80% green to NS. Baseline wastes 50% on EW. Watch NS queue drain rapidly under optimizer while EW queue stays short
2 — Full Day demo_full_day 480s (fast-forward) Full weekday cycle: quiet night → AM rush → symmetric midday → PM rush (EW-dominant) → evening Light state pattern flips at 8am (NS dominant) then again at 5pm (EW dominant)
3 — Incident demo_incident 300s simulated AM rush + accident blocks north approach of intersection 0 by 85% at t=150s. Road clears at t=240s. ⚠ t=150s: queue collapses on north, optimizer detects via queue feedback and reallocates green. ✓ t=240s: recovery.
